# QATFactory Quantization-Aware RL

GRPO where the sampling policy *is* the deployed policy: a colocated vLLM engine serves the
packed `nvfp4-pack-quantized` export, the trainer optimizes BF16 latents through the NVFP4
straight-through quantizer, and after every optimizer step the latents are re-packed and
published into the live engine.

| Component | Location |
|-----------|----------|
| Weight publisher (vLLM layer mapping, packing, in-place publish) | `qatfactory/rl/vllm_nvfp4_sync.py` |
| Student construction + startup gates | `qatfactory/rl/model.py` |
| `QuantGRPOTrainer` + NVFP4 generation backend | `qatfactory/rl/grpo_trainer.py` |
| Entry point | `scripts/train_llm_qarl.py` |
| Bit-exactness verifier | `scripts/verify_qarl_sync.py` |
| Config | `configs/llm/qwen3_8b_nvfp4_qarl.yaml` |
| Launcher (verify → train → export) | `examples/run_qarl_qwen3_8b.sh` |

## Two models, two roles

- **`model.model_path`** — the BF16 latents that actually train. A Hub repo id or local
  directory: `Qwen/Qwen3-8B` to RL the base model, or a QAD checkpoint to continue from one.
- **`model.rollout_path`** — the `nvfp4-pack-quantized` export vLLM serves. It supplies the
  architecture, quantization config, tokenizer, the frozen tensors, and the starting static
  activation scales (which the run pins to unless `qad.sync_activation_scales` is on).

They must agree: startup refuses to proceed unless the architectures match **and every
frozen tensor is bit-identical**, because QARL syncs only the quantized linears — anything
else in the engine comes from the export and would silently diverge.

## Supported scope

- Dense Qwen3 NVFP4, `vllm_mode: colocate`, `vllm_tensor_parallel_size: 1`, GRPO.
- Server mode is rejected: the publisher mutates packed tensors inside the engine process,
  which needs the in-process engine (`distributed_executor_backend="external_launcher"`).
- Only quantized-linear latents train; `apply_fake_quant` freezes and enforces everything
  else, so the rollout engine's non-quantized tensors never need updating.
- LoRA-QARL, MoE, and MXFP4/Q4_K rollout engines are not wired up — reject them explicitly.

## Environment

Needs `trl`, `vllm` and `math-verify` (for `accuracy_reward`) on top of the base
dependencies. Note that a `torchaudio` built against a different CUDA version than `torch`
makes `import vllm` fail through `transformers.audio_utils`; remove or match it.

## Workflow

1. Read the config. Confirm the rollout export exists and was built
   from the intended latents.
2. **Verify the weight sync before training.** Point `verify_qarl_sync.py` at an export and
   the latents it was built from; re-packing must reproduce the served checkpoint bit for
   bit, so the first sync is a no-op. This exercises the whole path against the real kernel.
3. Run a bounded smoke (few steps, short completions, 2–4 GPUs) before a full run.
4. Launch, then watch `sampling/sampling_logp_difference/mean` from the first logged step —
   it is the online proof that sync and scale tying are correct. Also watch `reward`,
   `completions/clipped_ratio`, `grad_norm`, and OOM/NaN.
5. Outputs are an ordinary QAD-shaped checkpoint (BF16 latents, `qatfactory_qad` metadata,
   `input_scales.safetensors`), so `/qatfactory-nvfp4-export` re-exports the RL-tuned policy
   unchanged.

## Command

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 PYTORCH_ALLOC_CONF=expandable_segments:True \
torchrun --nproc_per_node=8 scripts/train_llm_qarl.py \
  configs/llm/qwen3_8b_nvfp4_qarl.yaml \
  --model.rollout_path <export dir> --wandb.project qatfactory-qarl
```

Bounded smoke (2 GPUs, 3 steps):

```bash
CUDA_VISIBLE_DEVICES=0,1 PYTORCH_ALLOC_CONF=expandable_segments:True \
torchrun --nproc_per_node=2 scripts/train_llm_qarl.py \
  configs/llm/qwen3_8b_nvfp4_qarl.yaml \
  --data.eval_split null --data.max_train_samples 64 \
  --train.max_steps 3 --train.per_device_train_batch_size 4 --train.num_generations 4 \
  --train.gradient_accumulation_steps 1 --train.max_completion_length 128 \
  --train.save_strategy no --train.vllm_gpu_memory_utilization 0.15 \
  --train.vllm_max_model_length 1024 --train.output_dir outputs/qarl_smoke --wandb.enable false
```

Any config value takes a dotted CLI override, as elsewhere in the repo. Or run the whole
verify → train → export pipeline: `bash examples/run_qarl_qwen3_8b.sh`.

## Configuration notes

- `qad.quantize_activations`: `false` (default) trains weight-only W4A16; `true` also
  fake-quantizes linear inputs with the step-static scale. Measured on Qwen3-8B, `true`
  does **not** shrink the sampler/trainer gap (0.072–0.078 vs 0.058–0.075 nats) — the
  residual is engine-versus-trainer numerics, not the activation quantization — so prefer
  `false` unless you want to optimize the W4A4 objective specifically.
- `qad.sync_activation_scales`: `false` (default) keeps the export's activation scales for
  the whole run, and the publisher never touches `input_global_scale`. `true` tracks a
  running maximum over each linear's inputs during training and publishes the fused-family
  reduction to vLLM with every weight sync, which is what you want when the export's scales
  were calibrated on a different checkpoint (a grafted rollout export, say) rather than on
  the policy being trained.
- `qad.activation_scale_warmup_steps`: `8` by default; optimizer steps before the first
  scale publish. Only read when syncing is on. A running maximum only grows, so an early
  publish is premature rather than unsafe — this just lets the estimate settle instead of
  moving the rollout policy on every one of the first few syncs. Syncing is also deferred
  automatically until every target has been observed at least once.
- `train.vllm_gpu_memory_utilization` is a fraction of **total** device memory, not free
  memory. Keep it low (0.15–0.25) when sharing GPUs with other jobs.
- `train.num_generations` must divide `per_device_train_batch_size * world *
  steps_per_generation`.
- `beta: 0.0` avoids a reference model entirely; a nonzero KL would need a second copy.

## Verification

```bash
python -m pytest tests/rl tests/quant -q

CUDA_VISIBLE_DEVICES=0 python scripts/verify_qarl_sync.py \
  --latents <qad checkpoint> --rollout <its nvfp4 export>
```

Sanity signals for dense Qwen3-8B (36 layers): the publisher reports **144 vLLM layers
covering 252 quantized linears** (q/k/v fused into `qkv_proj`, gate/up into `gate_up_proj`);
startup verifies **147 frozen tensors** and reads **252 activation scales**; the verifier
compares 1155 engine tensors with zero differences. During training,
`sampling/sampling_logp_difference/mean` should sit in the low hundredths of a nat — a large
or growing value means the sync or the shared scales are wrong.
